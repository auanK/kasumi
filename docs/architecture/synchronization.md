# Synchronization

`kasumi sync <profile>` prepares the [runtime](application-and-runtime.md), recovers a pending [transaction](transactions-and-recovery.md), then collects local disk, accepted `StoredState`, and authenticated remote history. Local scan and remote observation can overlap. Remote history resolution produces an effective remote tree; [reconciliation](reconciliation.md) creates a candidate shared tree, an ordered `SyncPlan`, and flags for physical repair, local mutation, publication, or accepted-state commit.

## Initial Sync

`kasumi sync <profile> --initial` initializes a missing local database and admits two valid scenarios:

1. **Bootstrap (Empty Remote History):** When the remote history namespace is empty, initial sync publishes new genesis history from the local files and can reuse compatible pre-existing Content.
2. **Enrollment (Existing Authenticated Remote Vault):** When valid authenticated remote history already exists, an uninitialized client observes the accepted remote history and enrolls into the vault, reconciling its local files against the remote tree. If the remote history contains partial, unrecognized, or corrupted objects without authenticated head markers, the operation fails closed before creating the local database.

Under the profile lock, initial sync rejects SQLite sidecars (`-wal`, `-shm`, `-journal`) and transaction evidence, resolves the existing vault key, and inspects local state without following symlinks. An empty, valid pre-existing local database without accepted state (such as from an interrupted initial run) is safely reused without manual deletion, provided no transaction recovery evidence exists.

### Trusted Pre-existing Content (`--trust-existing-content`)

`kasumi sync <profile> --initial --trust-existing-content` is an opt-in bootstrap optimization that allows an uninitialized client bootstrapping against an empty remote history namespace to reuse pre-existing remote Content matching logical ciphertext identifiers without performing speculative download and verification GETs. Pre-existing trusted content is tracked separately (`trusted_remote_content_objects`), and redundant upload PUTs are elided.

- **Scope:** Strictly valid only during bootstrap with an empty remote history namespace. It cannot be combined with any command other than `sync --initial`.
- **Concurrency Protection:** If remote history is observed concurrently during initial observation or stabilization, the operation is immediately rejected to prevent unverified content reuse or concurrent genesis publication.
- **Enrollment Isolation:** Enrollment into an existing vault never performs speculative orphan content audit, ensuring normal deduplication and payload validation standards.
- **Security:** Content reused via `--trust-existing-content` is assumed valid based on key and hash derivation without payload AEAD authentication. A warning is presented advising subsequent `kasumi fsck` for offline verification. Subsequent normal syncs do not implicitly re-audit trusted content and suffer zero performance overhead.

## Required Content Availability

Normal Sync checks only the deduplicated Content IDs needed by the current work: Download operations, relevant pending materialization/storage rows, and accepted remote rows whose `hash:size` matches a planned Upload that may be elided by deduplication. A new Upload is sent directly and does not require a presence preflight. A true no-op has no operational Content IDs to check, so it performs no content-presence probe or full inventory; it still recovers pending transactions and authenticates the observed remote history. Pending-deletion authority keeps its existing scoped behavior and never expands into an implicit logical deletion.

The probe uses `control_read_batch` when the transport exposes it and falls back to individual `presence` checks. A transport or cancellation failure is an error, never evidence of absence. When a complete physical content inventory is already available, Sync cross-checks LIST and PRESENCE in both directions and fails closed on disagreement; LIST omission alone never proves that a required object is missing. Missing required IDs are returned to reconciliation, which deduplicates repair uploads by plaintext hash. The upload path requires a regular non-symlink local source and verifies its bytes against the expected logical hash and size, independently of cached fingerprints. A mismatch fails before PUT and preserves accepted logical state and recovery evidence. If no compatible source exists, Sync preserves the logical rows, accepted Commit/HEAD, expected Content IDs, local state, and pending evidence, records pending paths, and returns a partial result (exit status `2`). Missing objects unrelated to current work are not discovered or repaired by ordinary Sync; use Fsck or remote-content inspection to check broader availability. Sync never infers a logical deletion or invokes `resolve-missing` automatically.

## Optional Remote Inventory Audit

`kasumi sync <profile> --audit-inventory` runs normal Sync first and performs the audit when Sync returns a summary, including a partial result. The audit uses authenticated remote history and two complete physical object listings. The ordinary command without this flag does not list the full namespace, so its cost remains independent of unrelated remote Content IDs. This command retains normal Sync's possible local and remote effects; only the subsequent audit phase is read-only. `--audit-inventory` cannot be combined with `--dry-run` or `--initial`.

The summary counts Content IDs referenced by reachable Commits across retained history, not only the latest tree. A referenced ID is **present** when its identifier occurs in the physical listing and **missing** when it does not. A physical Content ID is an **orphan** only when no reachable Commit references it; removal from the latest tree alone does not make historical content an orphan. **Unknown** counts physical identifiers that the existing remote object classifier does not recognize as structurally valid. These are namespace and reachability checks: they do not download or authenticate Content payload bytes and are not a substitute for Fsck or `remote contents <profile> --audit`.

The audit phase does not upload, repair, delete, quarantine, publish, or alter accepted state. It rejects a failed listing, incomplete authenticated history, active writers or maintenance barriers observed in the initial listing, and changes detected between the initial and final full listings as inconclusive. The two listings are observations, not an atomic snapshot: identical results cannot rule out an object being created and removed, replaced under the same identifier, or a writer starting and finishing between observations. A clean result means no inconsistency was detected in the observations; it does not prove the absence of concurrency or authenticate Content payload bytes. A complete Sync with no findings returns `0`; findings or a partial Sync return `2`; audit failure returns `1`. If the audit fails after Sync published a Commit, the error reports that Sync completed and the publication remains remote; there is no rollback.

Scoped remote observation may use the accepted Commit as a `cached_anchor` only
after proving ancestry linkage for all loaded branches. A concurrent sibling
head need not descend from that anchor, even if its marker remains visible;
loading then retries without the cached anchor to recover the common ancestry.
The resulting authenticated multi-head history is reconciled and can produce a
multi-parent merge Commit. See [History and Concurrency](history-and-concurrency.md#cached-anchors-and-scoped-observation).

Sync registers a remote writer when active work is needed, including publication, repair, local mutation, or state commit. Writer markers admit multiple clients concurrently while blocking [GC](garbage-collection.md) from starting destructive maintenance. A repair-only run is admitted through the same registration path; an active GC barrier stops it before effects. If initial history is absent, sync initializes the remote transport before publication. A true no-op creates no Commit and may update the local file-hash cache.

## Stabilize Before Effects

The coordinator starts from the caller's required-content probe and reconciliation, verifies destructive local file targets independently of cached hashes, stages plan inputs, reobserves remote and local state, probes the required Content again, re-reconciles, and compares the observations. A content mismatch updates the observed row, invalidates its cache entry, and triggers reconciliation before effects. Unexpected disappearance, replacement by a non-regular entry, or an occupied rename/download destination stops the operation. If inputs changed, stabilization retries within a three-attempt bound; repeated movement yields `ConcurrentModification`. A remote publication after this window is still possible: immutable Commit/HEAD objects preserve both branches for later resolution. Missing download payloads discovered during execution trigger bounded replan attempts; repeated disappearance also fails instead of applying an unsafe stale plan. [Local Observation](local-observation.md) owns scan and cache rules.

## Execute and Validate

The transaction journal records the validated plan and per-operation progress. Staging preserves previous local content before mutation. Content uploads are encrypted, downloaded plaintext is authenticated and hash-checked before installation, and logical remote actions update the intended tree. Existing Download destinations are atomically replaced; absent destinations use installation that fails if another entry appeared. `DeleteLocal` and `RenameLocal` use the prepared content/type checks, with rename installation refusing an occupied destination. Work follows the plan's dependency phases, with bounded transfer concurrency and optional transport batches. Repair-only work publishes no Commit or HEAD and uses the local-only journal/recovery contract. See [Reconciliation](reconciliation.md#reconciliation-and-syncplan) for the plan and pending-file model and [Transactions and Recovery](transactions-and-recovery.md#per-operation-state-and-branching) for repair recovery.

The final local validation and the filesystem syscall are separate operations. External writers can still change the destination in that interval or write through an open handle after a rename; that race can overwrite, remove, or move their edit. If a destination conflict is detected before that operation has an effect, the transaction is cleared while completed peer effects remain on disk, and Sync returns `ConcurrentModification`; the next Sync reobserves and replans rather than replaying the old plan. Other failures use the established rollback/resume path; if recovery becomes ambiguous, its journal and backups remain. See [Transactions and Recovery](transactions-and-recovery.md#local-mutation-contract-and-external-writers).

After applying effects, sync restores required timestamps, scans disk again, and builds the **publication tree** from observed materialized rows plus pending remote rows. New unrelated local paths that appeared during execution stay on disk for a later run. Changes to expected rows fail validation and roll back local mutations. A local-only run validates against its pinned remote head and commits that accepted state to SQLite without publishing a Commit.

If publication is required, sync prepares a canonical Commit whose parents are the sorted logical heads from the stabilized observation (none for bootstrap). The encrypted Commit variant is uploaded or safely reused and verified before a physical HEAD marker is uploaded and verified. A genesis Epoch follows bootstrap; later authenticated Epochs may advance a safe retention frontier. Only after those remote checks does SQLite accept the new `StoredState`; observed ancestral markers are then pruned and the journal/workspace cleaned. [Remote Layout and Publication](remote-layout.md) defines identities, ordering, and physical verification. Publication can overlap local transfer work, but the marker remains behind Commit verification and final local-tree validation.
