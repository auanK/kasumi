# Synchronization

`kasumi sync <profile>` prepares the [runtime](application-and-runtime.md), recovers a pending [transaction](transactions-and-recovery.md), enforces empty-local safety guards (blocking with `empty_local_blocked` if a missing `local_dir` or emptied >5-entry populated tree would trigger mass remote deletion, unless `allow_empty_local` is explicitly set), then collects local disk, accepted `StoredState`, and authenticated remote history. Local scan and remote observation can overlap. Remote history resolution produces an effective remote tree; [reconciliation](reconciliation.md) creates a candidate shared tree, an ordered `SyncPlan`, and flags for physical repair, local mutation, publication, or accepted-state commit.

## Initial Sync

`kasumi sync <profile> --initial` initializes a missing local database and admits two valid scenarios:

1. **Bootstrap (Empty Remote History):** An empty listing makes the local files candidates for genesis and allows reuse of compatible content. Immediately before parentless publication, the registered initializer checks it is the only visible writer and rereads HEAD and Epoch. A competing writer or unexpected history stops admission.
2. **Enrollment (Existing Authenticated Remote Vault):** When valid authenticated remote history already exists, an uninitialized client observes the accepted remote history and enrolls into the vault, reconciling its local files against the remote tree. If the remote history contains partial, unrecognized, or corrupted objects without authenticated head markers, the operation fails closed before creating the local database.

Under the profile lock, initial sync rejects SQLite sidecars (`-wal`, `-shm`, `-journal`) and transaction evidence, resolves the existing vault key, and inspects local state without following symlinks. An empty, valid pre-existing local database without accepted state (such as from an interrupted initial run) is safely reused without manual deletion, provided no transaction recovery evidence exists.

## Required Content Availability

Normal Sync checks only the deduplicated physical object IDs (loose Content IDs, `KPAK\x01` Pack IDs, and FastCDC chunk Content IDs resolved through the effective `StorageManifest`) needed by the current work: `Download` and `CopyLocal` operations, relevant pending materialization/storage rows, and accepted remote rows whose `hash:size` matches a planned Upload that may be elided by deduplication. `MoveLocal` operations satisfy destination paths directly from verified local sources without probing, downloading, uploading, or copying remote `Content`, and local file or directory renames whose accepted source paths are removed from the candidate shared tree reuse accepted remote `Content` without remote `PRESENCE` queries. A new Upload is sent directly and does not require a presence preflight (except for FastCDC chunked uploads, which probe whether individual chunks already exist remotely so unchanged chunks are skipped). A true no-op has no operational Content IDs to check, so it performs no content-presence probe or full inventory; it still recovers pending transactions and authenticates the observed remote history. Pending-deletion authority keeps its existing scoped behavior and never expands into an implicit logical deletion.

`CopyLocal` materializes files from verified local bytes while still checking the required remote Content (loose, packed, or chunked physical objects) with `PRESENCE`. When that Content is present, the copy performs no Content GET, PUT, or remote COPY. If it is missing, reconciliation schedules a repair Upload from a local source matching the expected hash and size and preserves the local materialization. A physical-only repair publishes no new Commit or HEAD, and a failed required repair remains an error.

When a required presence check finds an absent Micro-Pack, Sync uses that result for every member of the pack in the effective manifest. A physical-only repair succeeds only when verified local members reproduce the original Pack ID. If the same sync already needs to publish a Commit, it can replace the old mapping with new packs or loose objects for the remaining members, provided every required source is available. Retained historical Commits can still reference the old Pack ID.

`DeleteIgnoredLocalFile` does not transfer or publish Content. It is planned only
for a regular file matched by a `(?d)` rule when an accepted managed directory
removal authorizes the containing subtree's removal. The scanner hashes only
selected candidates. Sync verifies the recorded file identity, size, hash, and a
durable transaction backup before removal. Recovery can restore the file if the
transaction rolls back; conflicts preserve external replacements. `PRESENCE`
checks for other required Content remain independent of this local removal.

When the probe batch contains FastCDC chunked objects and at least 8 physical IDs, Sync uses a single `transport::list(storage)` call to resolve physical presence in bulk; otherwise it uses `control_read_batch` when the transport exposes it and falls back to individual `presence` checks. A transport or cancellation failure is an error, never evidence of absence. When a complete physical content inventory is already available, Sync cross-checks LIST and PRESENCE in both directions and fails closed on disagreement; LIST omission alone never proves that a required object is missing. Missing required IDs are returned to reconciliation, which deduplicates repair uploads by plaintext hash. The upload path requires a regular non-symlink local source and verifies its bytes against the expected logical hash and size, independently of cached fingerprints. A mismatch fails before PUT and preserves accepted logical state and recovery evidence. If no compatible source exists, Sync preserves the logical rows, accepted Commit/HEAD, expected Content IDs, local state, and pending evidence, records pending paths, and returns a partial result (exit status `2`). Missing objects unrelated to current work are not discovered or repaired by ordinary Sync; use `kasumi sync <profile> --repair` for fast single-listing missing-object recovery from verified local sources (without downloading payloads like `fsck` or publishing a new Commit when only physical repair occurs; incompatible with `--dry-run` and `--initial`), or use Fsck / remote-content inspection to audit payload integrity. Sync also runs a local free disk-space preflight check before planning or staging downloads and fails cleanly with `insufficient_disk_space` if available space on the profile's local directory or staging parent is below the required download footprint. Sync never infers a logical deletion or invokes `resolve-missing` automatically.

## Adaptive Transfer Execution: Micro-Packs (`KPAK\x01`), FastCDC, and Protocol v3

During the upload and download staging phases, the coordinator adapts physical transfers according to file size and the effective `StorageManifest`:

* **Protocol v3 In-Memory Compression (`KASUMI\x03\x00`)**: Every uploaded loose file, FastCDC chunk, `KPAK\x01` Micro-Pack, and Commit payload is split into `1 MiB` plaintext chunks, compressed in RAM with Zstandard (`zstd` level 1) when compression saves more than 32 bytes (skipping consecutive incompressible `>= 64 KiB` frames after 2 misses while re-probing every 16th frame), and encrypted with XChaCha20-Poly1305 binding its `FilePurpose` (`Content`, `History`, or `Pack`).
* **Small-file packing.** Sync can group eligible uploads of up to 256 KiB into packs targeting 4 MiB. Candidate count and transport capabilities determine whether a group is packed. Unpacked candidates stay loose. The new manifest records the member hash, size and logical pack hash. The pack's own table gives the byte offset. [Physical layout and writer thresholds](remote-layout.md)
* **Large-File Adaptive FastCDC Chunking (`> 8 MiB`) and Delta Upload**. Uploads larger than `8 MiB` use size-tiered normalized Gear FastCDC (`256 KiB`–`4 MiB` with a `1 MiB` average up to `64 MiB`, `1 MiB`–`16 MiB` with a `4 MiB` average up to `512 MiB`, and `4 MiB`–`32 MiB` with a `16 MiB` average above `512 MiB`). Sync computes layouts for independent files in parallel and validates each file against the plan. It checks slice identity and BLAKE3 during encryption and writes the ordered slices to `StorageManifest.chunked_files`.
* **Chunked Upload Retry**. Sync probes the candidate Content IDs and uses one listing when at least eight IDs can be checked in bulk. It authenticates and hashes any matching object outside the observed live manifest before reusing it. A retry can recover valid chunks from an interrupted first upload even after the local journal rolls back. Missing or unverified chunks are encrypted and uploaded in windows of at most 64 chunks and 256 MiB of plaintext.
* **Bounded Manifest Prefetch and Client-Side FastCDC Delta Download**. Sync extracts requested Micro-Pack members into private staged files. It downloads and decrypts at most 64 FastCDC chunks and 256 MiB of plaintext per window. Sync checks each chunk's size and BLAKE3, removes encrypted scratch after verification, and removes each plaintext chunk after copying it into the staged file. Verified slices in staged files supply later copies of the same chunk, including across files. Local seed slices are checked for identity and BLAKE3 before reuse. Assembly hashes the file in logical order, and installation verifies the on-disk candidate before replacing the destination.

## Optional Remote Inventory Audit

`kasumi sync <profile> --audit-inventory` runs normal Sync first and performs the audit when Sync returns a summary, including a partial result. The audit uses authenticated remote history and two complete physical object listings. Ordinary Sync uses full listings when it can resolve large batches of FastCDC presence checks in bulk. This command retains normal Sync's possible local and remote effects; only the subsequent audit phase is read-only. `--audit-inventory` cannot be combined with `--dry-run` or `--initial`.

The summary counts Content IDs referenced by reachable Commits across retained history, not only the latest tree. A referenced ID is **present** when its identifier occurs in the physical listing and **missing** when it does not. A physical Content ID is an **orphan** only when no reachable Commit references it; removal from the latest tree alone does not make historical content an orphan. **Unknown** counts physical identifiers that the existing remote object classifier does not recognize as structurally valid. These are namespace and reachability checks: they do not download or authenticate Content payload bytes and are not a substitute for Fsck or `remote contents <profile> --audit`.

The audit phase does not upload, repair, delete, quarantine, publish, or alter accepted state. It rejects a failed listing, incomplete authenticated history, active writers or maintenance barriers observed in the initial listing, and changes detected between the initial and final full listings as inconclusive. The two listings are observations, not an atomic snapshot: identical results cannot rule out an object being created and removed, replaced under the same identifier, or a writer starting and finishing between observations. A clean result means no inconsistency was detected in the observations; it does not prove the absence of concurrency or authenticate Content payload bytes. A complete Sync with no findings returns `0`; findings or a partial Sync return `2`; audit failure returns `1`. If the audit fails after Sync published a Commit, the error reports that Sync completed and the publication remains remote; there is no rollback.

Scoped remote observation may use the accepted Commit as a `cached_anchor` only
after proving ancestry linkage for all loaded branches. A concurrent sibling
head need not descend from that anchor, even if its marker remains visible;
loading then retries without the cached anchor to recover the common ancestry.
The resulting authenticated multi-head history is reconciled and can produce a
multi-parent merge Commit. See [History and Concurrency](history-and-concurrency.md#cached-anchors-and-scoped-observation).

Sync registers a remote writer when active work is needed, including publication, repair, local mutation, or state commit. Writer markers admit multiple clients concurrently while blocking [GC](garbage-collection.md) from starting destructive maintenance. A repair-only run is admitted through the same registration path; an active GC barrier stops it before effects. If initial history is absent, sync initializes the remote transport before publication. A true no-op creates no Commit and may update the local file-hash cache.

## Stabilize Before Effects

The coordinator starts from the caller's required-content probe and reconciliation, verifies destructive local file targets independently of cached hashes, stages plan inputs, reobserves remote and local state, probes the required Content again, re-reconciles, and compares the observations. A content mismatch updates the observed row, invalidates its cache entry, and triggers reconciliation before effects. Unexpected disappearance, replacement by a non-regular entry, or an occupied rename/download destination stops the operation. If inputs changed, stabilization retries within a three-attempt bound; repeated movement yields `ConcurrentModification`. A remote publication after this window is still possible: immutable Commit/HEAD objects preserve both branches for later resolution. Missing download payloads discovered during execution trigger bounded replan attempts; repeated disappearance also fails instead of applying an unsafe stale plan. [Local Observation](local-observation.md) owns scan and cache rules.

Stabilization also refreshes transient physical evidence of ignored entries. A change to ignored directory contents can leave the managed Snapshot unchanged while altering which physical directories may safely be removed. The updated evidence is incorporated into the recalculated reconciliation plan before effects. Ordinary changes to ignored cache contents do not require treating every physical evidence difference as a new logical synchronization change.

## Execute and Validate

The transaction journal records the validated plan and per-operation progress. Staging preserves previous local content before mutation. Content uploads are encrypted, downloaded plaintext is authenticated and hash-checked before installation, and logical remote actions update the intended tree. Existing Download destinations are atomically replaced; absent destinations use installation that fails if another entry appeared. `DeleteLocal`, `RenameLocal`, and `MoveLocal` use the prepared content/type checks, with `RenameLocal` and `MoveLocal` installation refusing an occupied destination and `MoveLocal` additionally verifying expected file size and BLAKE3 hash before moving. Work follows the plan's dependency phases, with bounded transfer concurrency and optional transport batches. Repair-only work publishes no Commit or HEAD and uses the local-only journal/recovery contract. See [Reconciliation](reconciliation.md#reconciliation-and-syncplan) for the plan and pending-file model and [Transactions and Recovery](transactions-and-recovery.md#per-operation-state-and-branching) for repair recovery.

The final local validation and the filesystem syscall are separate operations. External writers can still change the destination in that interval or write through an open handle after a rename; that race can overwrite, remove, or move their edit. If a destination conflict is detected before that operation has an effect, the transaction is cleared while completed peer effects remain on disk, and Sync returns `ConcurrentModification`; the next Sync reobserves and replans rather than replaying the old plan. Other failures use the established rollback/resume path; if recovery becomes ambiguous, its journal and backups remain. See [Transactions and Recovery](transactions-and-recovery.md#local-mutation-contract-and-external-writers).

After applying effects, sync restores required timestamps, scans disk again, and builds the **publication tree** from observed materialized rows plus pending remote rows. New unrelated local paths that appeared during execution stay on disk for a later run. Changes to expected rows fail validation and roll back local mutations. A local-only run validates against its pinned remote head and commits that accepted state to SQLite without publishing a Commit.

Directory removal remains non-recursive. A directory retained solely for ignored content is not physically removed or included in the resulting managed publication tree. Final local observation collects fresh ignore evidence and projects the materialized tree before checking it against the reconciled candidate. A directory unexpectedly occupied after stabilization causes a conflict rather than authorizing recursive deletion or silently treating the removal as successful.

If publication is required, sync prepares a canonical Commit whose parents are the sorted logical heads from the stabilized observation (none for bootstrap). The encrypted Commit variant is uploaded or safely reused and verified before a physical HEAD marker is uploaded and verified. Genesis admission checks that the registered initializer is alone and then checks the remote HEAD and Epoch namespaces. A genesis Epoch follows the first HEAD. Ordinary 0.32 Sync validates and adopts any confirmed Epoch frontier (retaining `expired_base_tree` read-only if an offline device's local base fell behind a newly advanced anchor so untouched files fast-forward while local edits are preserved cleanly) and keeps `DeferMultiWriter` on established vaults; [`kasumi gc`](garbage-collection.md) advances the pruning Epoch under cooperative maintenance exclusion. Only after those remote checks does SQLite accept the new `StoredState`; observed ancestral markers are then pruned and the journal/workspace cleaned. [Remote Layout and Publication](remote-layout.md) defines identities, ordering, and physical verification. Publication can overlap local transfer work, but the marker remains behind Commit verification and final local-tree validation.

## Other Operations

`sync --dry-run` is [Preview](planning-and-status.md), not this execution path; `status` shares its planner. [Fsck](fsck.md) and [Garbage Collection](garbage-collection.md) run transaction recovery before their own distinct maintenance lifecycles.

## Live execution progress

Sync samples counters from local observation, upload staging, transport, verification, and installation. Transfer totals count encoded payloads, including validation readbacks and repeated transfers. The reuse counter tracks verified seed slices and eligible upload deduplication. Reobservation is labeled with its retry attempt. Progress introduces no presence checks or listings in no-op sync or active sync.
