# Effective Tree and Content Inspection

These commands use the [common inspection path](remote-inspection.md). By default, `stat`/`get`/`restore` address the authenticated **effective tree** after concurrent logical heads are resolved; when `--commit <id>` is supplied, they bypass `cached_anchor` and inspect that specific reachable commit's Snapshot and `StorageManifest` directly, while `tree` displays one selected current head's Snapshot. [History and Concurrency](history-and-concurrency.md) owns the merge rules, and [Security](../security.md) owns the content encryption and identifiers.

| Command | Input/view and validation | Effects and failure boundary |
|---|---|---|
| `remote stat <path> [--commit <id>]` | Resolve a portable logical path (`/` denotes the root) in the observed effective tree or selected reachable commit; report NodeRow type, logical hash, size, time, and observed height/conflicts context. | No file-content download, destination write, or remote mutation. Missing/invalid path or unreachable commit fails. |
| `remote get <path> <dst> [--commit <id>]` | Require a file in the effective tree or selected reachable commit; resolve its physical representation via its `StorageManifest` (extracting its slice from a `KPAK\x01` Micro-Pack, downloading and reassembling its FastCDC chunks into a private temporary file, or downloading its loose Content ID), AEAD-decrypt, then verify whole-file plaintext BLAKE3 and size against the NodeRow. | Validate the local destination/parent (including unsafe-link and file-type checks), write a private temporary file, and atomically install the verified plaintext with durability steps. Missing/invalid bytes, unreachable commit, or unsafe destination fail before accepting the update. This is an explicit local write, not a Sync transaction; choosing a destination inside the synchronized tree is the caller's responsibility. |
| `remote restore [<prefix>] <dst> [--commit <id>] [--dry-run]` | Resolve root `/` (when `<prefix>` is omitted), a subdirectory, or a single file in the effective tree or selected reachable commit; verify destination is a non-overlapping, safe empty (or not-yet-created) directory beneath a safe parent; deduplicate shared content hashes, `KPAK\x01` packs, and FastCDC chunks; AEAD-decrypt and verify every payload against its NodeRow. | With `--dry-run`: zero downloads and zero disk writes. Real run: creates target directory structure cleanly and installs verified files with atomic temporary writes and preserved mtimes. Fails before modifying `<dst>` if overlaps `local_dir` or is non-empty. |
| `remote contents` | Load complete authenticated reachable history, collect physical object references (loose Content IDs, `KPAK\x01` Pack IDs, and FastCDC chunk Content IDs) from the effective tree and reachable Commit Snapshots/`StorageManifest` records, and join them to the physical content listing. Store each logical path once per physical ID. Report referenced/current, present, missing, and orphan physical IDs. | Reports structural presence. Payload verification requires an audit. |
| `remote contents <profile> --audit` | Build the same inventory, then GET **every physically present content/pack/chunk object**, including orphans. AEAD-decrypt it (`FilePurpose::Content` or `FilePurpose::Pack`), validate pack members (`KPAK\x01`) or chunk/loose plaintext hashes, and verify the keyed Content ID or Pack ID. Use [Fsck](fsck.md) to verify the whole-file BLAKE3 of a chunked file. | Reports valid/invalid/missing per entry. A listing/GET race can turn a listed object into missing. Transport failures abort the report. |
| `remote content <id>` | Build the same complete-history structural inventory as `contents`, then select one Content or Pack ID and report its references/presence. | Does **not** audit that payload; absent ID is an error. Use `contents <profile> --audit` for byte validation. |

`remote get` authenticates only the requested file payload, while `contents <profile> --audit` audits physically present content across the inventory. [Fsck](fsck.md) instead audits every **referenced** object, reports progress, and first recovers an interrupted Sync. Neither structural `contents` nor `remote health` is a substitute for either payload audit. No content-inspection command publishes or deletes remote objects.

## Relationship to Sync repair

Normal [Sync](synchronization.md#required-content-availability) does not certify that every Content ID referenced by the vault is physically available. It probes only the deduplicated IDs required by its current work: Downloads, relevant pending rows, and accepted rows sharing a `hash:size` identity with a planned Upload that may be elided by deduplication. New Uploads are published directly. A no-op does not probe content presence or build a physical inventory. When a complete inventory has already been obtained, Sync cross-checks required IDs against PRESENCE and fails closed on disagreement; a LIST omission alone is not treated as proof of absence.

`kasumi sync <profile> --audit-inventory` opts into a structural inventory after normal Sync returns. It reuses authenticated history reachability and the existing Content inventory classifier, then compares two complete physical listings. This detects changes visible between those listings, but they are not an atomic snapshot: matching results cannot rule out transient changes, replacement under the same identifier, or a writer that starts and finishes between observations. Detected writers or barriers, transport failures, incomplete history, or changed listings produce an explicit inconclusive error instead of a report. The summary is limited to referenced/present/missing Content, orphan Content, and unknown physical objects. Reachability includes retained historical Commits, so a Content ID absent from the latest tree can still be referenced. A clean result means no inconsistency was detected in the observations; it does not authenticate payload bytes or prove the absence of concurrent changes. This mode does not download Content payloads, repair, or remove objects; it does not provide the cryptographic checks performed by Fsck or `remote contents <profile> --audit`. The Sync that runs before this read-only audit may still modify and publish state, and an audit failure does not roll it back. See [Optional Remote Inventory Audit](synchronization.md#optional-remote-inventory-audit) for exit status and publication behavior.

Inspection remains diagnostic. `remote contents` reports structural presence, `remote contents <profile> --audit` validates bytes, and neither repairs or publishes. Fsck checks referenced content across the accepted state. Ordinary Sync repairs an absent object when a current operation needs it and a valid source is available; absence in an unrelated file is left for explicit inspection or a later operation. Transport failures and LIST/PRESENCE disagreements must be investigated rather than converted into missing-content deletions.
