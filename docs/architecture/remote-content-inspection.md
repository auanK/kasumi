# Effective Tree and Content Inspection

These commands use the [common inspection path](remote-inspection.md). `stat`/`get` address the authenticated **effective tree** after concurrent logical heads are resolved; `tree` instead displays one selected head's Snapshot. [History and Concurrency](history-and-concurrency.md) owns the merge rules, and [Security](../security.md) owns the content encryption and identifiers.

| Command | Input/view and validation | Effects and failure boundary |
|---|---|---|
| `remote stat <path>` | Resolve a portable logical path (`/` denotes the root) in the observed effective tree; report NodeRow type, logical hash, size, time, and observed conflict/height context. | No file-content download, destination write, or remote mutation. Missing/invalid path fails. |
| `remote get <path> <dst>` | Require a file in the effective tree; derive its keyed Content ID from the committed logical hash, GET its ciphertext, AEAD-decrypt, then verify plaintext BLAKE3 and size against the NodeRow. | Validate the local destination/parent (including unsafe-link and file-type checks), write a temporary file, and atomically install the verified plaintext with durability steps. Missing/invalid bytes or unsafe destination fail before accepting the update. This is an explicit local write, not a Sync transaction; choosing a destination inside the synchronized tree is the caller's responsibility. |
| `remote contents` | Load complete authenticated reachable history, collect logical references from the effective tree and reachable Commit Snapshots, and join them to the physical content listing. Report referenced/current, present, missing, and orphan Content IDs. | Structural/availability inventory only: a present identifier is **not** proof of authentic payload bytes. Complete-history cache may be updated. |
| `remote contents --audit` | Build the same inventory, then GET **every physically present content object**, including orphans. AEAD-decrypt it, hash the plaintext, verify the keyed Content ID; for referenced content also check committed logical hash and size. | Reports valid/invalid/missing per entry, without a Fsck checkpoint, normal transaction recovery, repair, deletion, or accepted-state commit. A listing/GET race can turn a listed object into missing; transport failures abort the report. |
| `remote content <id>` | Build the same complete-history structural inventory as `contents`, then select one Content ID and report its references/presence. | Does **not** audit that payload; absent ID is an error. Use `contents --audit` for byte validation. |

`remote get` authenticates only the requested file payload, while `contents --audit` audits physically present content across the inventory. [Fsck](fsck.md) instead audits every **referenced** object, has private checkpoint/progress behavior, and first recovers an interrupted Sync. Neither structural `contents` nor `remote health` is a substitute for either payload audit. No content-inspection command publishes or deletes remote objects.

## Relationship to Sync repair

Normal [Sync](synchronization.md#required-content-availability) does not certify that every Content ID referenced by the vault is physically available. It probes only the deduplicated IDs required by its current work: Downloads, relevant pending rows, and accepted rows sharing a `hash:size` identity with a planned Upload that may be elided by deduplication. New Uploads are published directly. A no-op does not probe content presence or build a physical inventory. When a complete inventory has already been obtained, Sync cross-checks required IDs against PRESENCE and fails closed on disagreement; a LIST omission alone is not treated as proof of absence.

Inspection remains diagnostic. `remote contents` reports structural presence, `remote contents --audit` validates bytes, and neither repairs or publishes. Fsck checks referenced content across the accepted state. Ordinary Sync repairs an absent object when a current operation needs it and a valid source is available; absence in an unrelated file is left for explicit inspection or a later operation. Transport failures and LIST/PRESENCE disagreements must be investigated rather than converted into missing-content deletions.
