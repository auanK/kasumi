# Garbage Collection

`kasumi gc <profile>` performs destructive work only after its checks establish online reachability under the backend assumptions below. It quarantines unreachable content and unneeded physical Commit variants; it does not replace [Fsck](fsck.md)'s payload audit. Remote history, Epoch anchors, and the physical namespace are defined in [History and Concurrency](history-and-concurrency.md) and [Remote Layout and Publication](remote-layout.md).

## Admission and analysis

1. `application::execute` resolves the profile/key, validates retention, takes the **local** profile lock, and opens the [transport](transport.md). As with Fsck, pending [Sync transaction recovery](transactions-and-recovery.md) runs **before** GC, and can finish local or remote Sync effects or stop the operation on uncertainty.
2. GC publishes a verified, token-owned remote **barrier**. New Sync writers register their own visible writer marker and reject admission if the barrier is present. Normal Sync writers do **not** take a global publisher lock; they can coexist with each other. GC twice lists writer markers and re-verifies its own barrier between checks. Any observed active or abandoned marker, malformed control state, or observed loss of barrier ownership blocks collection rather than guessing liveness.
3. GC publishes a temporary provider-visibility probe, requires its presence in two listings, removes it, and requires its absence in two listings. If these observations show that safe online mutation cannot be established, GC returns **`analysis_only`** after one validated reachability/candidate snapshot: no quarantine restore, candidate removal, or purge. Barrier/probe creation and cleanup have already touched the remote. Probe errors fail rather than imply safety.
4. For online collection, GC inventories authenticated quarantine records, restores objects that have become reachable, and initializes missing metadata for prior quarantine objects. It then takes **two complete observations** of the physical namespace plus authenticated HEAD/Commit/Epoch reachability and content inventory. The observations must agree on logical heads, reachable Commits, required ciphertext variants, reachable content, candidates, and physical identifiers. A final listing must match before any destructive phase. Change, malformed history, unknown identifiers, missing required content, or an unsafe transport result stops collection.

The reachability walk retains current logical heads and the history required by authenticated Epoch anchors/retention; a reachable Commit needs its marked Ciphertext ID or a valid required variant, not every redundant variant. Candidate selection excludes retained content and required variants. Unknown/protected objects are **not** inferred safe to delete; Epoch objects are explicitly blocked from quarantine. This is why a raw `remote objects` listing is not a deletion list.

## Destructive phase and cleanup

5. After stable observation, GC **first purges previously quarantined entries** only if their authenticated metadata shows at least ten days of age, the original is still absent, they remain unreachable, they are not Epoch objects, their quarantined bytes match recorded physical SHA-256, and barrier ownership still holds. It removes metadata and then the quarantine object; partial failure is reported, not hidden.
6. New candidates are processed in bounded batches (up to eight). GC rechecks barrier ownership, obtains source physical SHA-256 when supported, copies to the keyed quarantine location using optional native/batch copy, and verifies destination SHA-256. If `physical_hash` or native copy is `Unsupported`, it uses a local workspace GET/PUT and readback with locally computed SHA-256. A non-`Unsupported` error or mismatch is not treated as permission to fall back blindly.
7. GC encrypts/authenticates quarantine metadata containing the timestamp and verified physical hash; the original identity is encoded in the quarantine path. It publishes and verifies the metadata (optional batch paths have verified individual fallbacks). Only after bytes **and** metadata are verified and the barrier is rechecked does it remove the original, using optional batch removal or sequential removal. Partial batch outcomes are reported; ambiguous batch failures are not blindly replayed. The result counts candidates, restored, newly quarantined, and purged objects.
8. GC checks barrier ownership before attempting release, closes the transport, and releases the local lock. If a replacement is visible at that check, it leaves the replacement in place. A replacement made after the check can still be removed by the subsequent ordinary `REMOVE`; this is another reason maintenance overlap is unsupported. Failures can leave a verified quarantine copy or metadata, an already removed source, or a control marker. GC has no local transaction journal for these mutations: the next run re-inventories and authenticates remote state, restores newly reachable objects, and applies retention rules rather than trusting an earlier partial result.

## Operational contract

**Warning — Concurrent garbage collection is unsupported.** Run only one GC or destructive maintenance operation per remote vault at a time, across all machines; running two GC commands simultaneously is unsupported. Normal GC, `purge-quarantine`, `repair-quarantine`, and manual writer-marker removal must not overlap. Pause scheduled and interactive Sync on every client before destructive maintenance and keep it paused until maintenance finishes. The local profile lock covers only processes using that profile on one machine. The remote barrier is a best-effort coordination mechanism built from ordinary storage operations. It can reduce the chance of overlap, but it is not a distributed lock or fencing mechanism; two maintenance commands can replace the shared barrier, and an ownership check can become stale before the next mutation.

Concurrent maintenance can leave remote state inconsistent, cause missing objects or interrupted cleanup, and result in permanent data loss. Recovery may require inspecting the remote vault and synchronizing again from clients that still have the affected content. Sync cannot recover content whose last available copy was deleted; restoration from an independent backup may be necessary.

The barrier still blocks a cooperating writer that observes it, and GC still aborts when its writer-marker observations find active or abandoned markers. Keep these checks in place, but do not treat them as a substitute for the operating rule above. `remote writers` and `remote health` are point-in-time observations; investigate conflicts and abandoned markers rather than deleting them indiscriminately.

The required `PUT`, `GET`, `LIST`, `PRESENCE`, and `REMOVE` operation names do not by themselves promise strong consistency. Destructive collection assumes the backend exposes completed changes to the listings and presence checks used by the protocol. The runtime probe tests visibility of its own newly published probe; passing it does not prove that every older object or writer marker is visible, nor certify provider-wide consistency. Confirm the backend's consistency guarantees independently. Do not use online destructive GC when those guarantees are unknown or insufficient. A returned `analysis_only` result means no quarantine restore, candidate removal, or purge occurred; it is not a selectable mode or proof that a backend which passed the probe is safe.

Remote copy verification protects **physical-byte preservation**, not plaintext validity. Optional provider SHA-256 is a performance capability; verified workspace fallback preserves the safety check without it. The barrier and repeated observations coordinate with normal cooperating writers and detect some visibility failures; they do not provide global exclusion or prevent an uncooperative actor from mutating storage. [Remote Maintenance Inspection](remote-maintenance-inspection.md) exposes candidate/control diagnostics without performing GC.

### Maintenance procedure

1. Stop Sync schedulers and active Sync processes on all clients using the vault.
2. Confirm that no GC, purge, repair, or writer-marker maintenance is active on another client.
3. Inspect `kasumi remote health <profile>` and `kasumi remote writers <profile>`. Identify any marker's owner before considering removal.
4. Confirm that the configured backend meets the consistency assumptions above; the runtime probe alone is not provider certification.
5. Run one maintenance command and inspect its result. Treat `analysis_only`, conflicts, and ambiguous transport errors as reasons to investigate before retrying destructive work.
6. Preserve quarantine payloads, metadata, and markers while resolving uncertainty. Do not delete protocol objects directly through the provider.
7. Resume normal Sync activity after maintenance has completed and its results have been inspected.

## Explicit quarantine maintenance (manual only)

These commands are separate from the retention-aware `kasumi gc <profile>` workflow:

```text
kasumi gc purge-quarantine <profile> --confirm-permanent-loss
kasumi gc repair-quarantine <profile> --confirm-permanent-loss
```

**`purge-quarantine` can permanently destroy referenced data.** Unlike normal GC, its explicit maintenance path does not use the normal 10-day retention/reachability decision as permission to delete. It requires the confirmation flag, establishes and verifies its own barrier, rejects observed writers and inadequate online-visibility guarantees, authenticates quarantine metadata, verifies quarantined physical bytes, checks original-object absence, and revalidates before removal. These precautions do **not** prove that the quarantined bytes are unnecessary or recoverable. The flag records deliberate acceptance of possible permanent loss; it is not evidence that an object is unreachable. If the quarantine payload is the only remaining copy, deletion is irreversible. Run purge alone under the operational contract above and preserve independent copies whenever there is doubt. Partial failures can leave incomplete quarantine pairs that require investigation.

**`repair-quarantine` is metadata cleanup, not payload repair.** It classifies quarantine pairs, refuses malformed, ambiguous, or payload-only entries, authenticates metadata and verifies eligibility before removing orphaned metadata whose quarantine payload is already absent. Healthy pairs are preserved; integrity failures block the operation. Run repair alone under the operational contract above; it does not establish reachability or recover missing content. Neither manual command should be automated as a substitute for normal GC.

`kasumi gc remove-writer <profile> <writer-id>` is a separate manual recovery operation. Take the exact identifier from `kasumi remote writers <profile>`; Kasumi verifies the keyed writer namespace and removes only that marker. It refuses removal when a maintenance barrier is present, but this check does not provide distributed exclusion. Kasumi cannot determine safely whether the associated process is still active, so the operator must verify that no Sync or maintenance operation is running before proceeding. It neither removes barriers nor runs Sync or GC. The ordinary GC writer checks remain unchanged.

Prefer `kasumi remote quarantine <profile>`, `kasumi remote health <profile>`, and `kasumi fsck <profile>` to understand the state before maintenance. Do not remove other remote protocol objects through the storage backend.
