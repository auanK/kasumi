# Kasumi 0.32 vault protocol

## Scope

Kasumi synchronizes directory snapshots between independently running clients through a passive object store. The unit of publication is a commit containing a canonical snapshot and its storage manifest. The unit of trust is a vault: all devices holding its master key have the same authority. The design allows concurrent branches, verifies their contents on clients, and makes interrupted local operations recoverable.

This contract fixes the externally observable rules for 0.32 clients. Application releases and format versions have separate numbering. A change in scheduling, parallelism, UI, cache layout, or storage provider can ship independently if it preserves the rules below.

## Participants and assumptions

| Participant | Assumption | Consequence if the assumption fails |
|---|---|---|
| Client | Trusted executable, OS account, cryptographic implementation and local checkpoint. One cooperating Kasumi operation holds the profile lock for mutation. | A key holder can author arbitrary valid history. Device names and timestamps cannot establish individual authorship. Local applications can edit files while Sync holds the lock. |
| Object store | For coordination, successful publication of an object is visible to subsequent GET and prefix LIST on **other devices**. Listings cover all entries in the relevant namespace. An object read yields a complete version or an error. | A stale, incomplete or equivocal listing can hide a peer, a branch, or an entire newer history. A client-side visibility probe can detect some violations. It cannot certify global consistency. |
| Operator | One vault key and one compatible control protocol per destination. Initialize a new destination with one device. Serialize destructive maintenance across devices and exclude out-of-band writers during it. | A writer that ignores a barrier, a forced removal of a live marker, or another tool deleting objects can invalidate a previously correct plan. |

The remote provider can read object lengths, identifiers, access times, control records and publication patterns. A client can authenticate the bytes it receives. The provider can withhold all copies of valid bytes, replay a previously valid view or present different views to different readers. A new client has no independent freshness witness. A returning client has the checks afforded by its retained local state. Independent backups are required for recovery from storage loss or a compromised vault key. [Security model](../security.md)

## Identities and formats

The CLI, daemon scheduler and authenticated Web API are entry points into the same local application. A browser session authorizes requests to that daemon. On storage, its operations use the profile's vault key and writer or maintenance registration. A queued job, watcher notification, warm transport or cached listing cannot substitute for the profile lock or publication checks. The local and rclone backends share the remote object contract. Their filesystem primitives and provider capabilities differ. [Application and runtime](application-and-runtime.md) · [HTTP API](../http-api.md) · [Transport](transport.md)

| Object | Stable interpretation |
|---|---|
| File, chunk or pack | The manifest maps logical content to loose, chunked or packed representations. BLAKE3 identifies logical bytes. Keyed, purpose-separated identifiers select remote objects. Verified materialization checks the expected logical content. The v3 file envelope uses client-side authenticated encryption. |
| Commit | Canonical `KCOM` v4 bytes bind a snapshot, sorted parents, height, timestamp, authorship and manifest. The keyed Commit ID identifies those bytes. The Ciphertext ID identifies one encrypted representation. Multiple ciphertext variants of the same commit are valid. |
| HEAD | The `KHED` v2 marker references a Commit ID and Ciphertext ID. A logical head is a marked commit with no other marked descendant in the accepted graph. Marker count and logical-head count can differ. |
| Epoch | `KEPO` v1 inside the `KEPA` v1 authenticated envelope binds the vault ID, sequence, issuance time, retention policy, anchors and predecessor. Within an accepted chain, each sequence has one identity. The accepted local reference contains both sequence and ID. |
| Local recovery and activity | The authenticated local journal records intended work and durable progress. Its codec v10 is a local recovery contract. Remote `KACT` v1 records convey activity. They confer no authority to accept a snapshot or delete an object. |

A `KCOM` v4 packed entry records the blob hash, size and logical pack hash. Its member offset lives inside `KPAK` v1. A chunked entry records the file identity and ordered slice hashes and sizes. Readers follow the authenticated manifest even if their writer would choose different packing thresholds. [Physical representations](remote-layout.md) · [File envelope](../security.md#encryption-standards)

Canonical field order, integer encoding, path validation, identifier derivations, domain separation and decoder bounds are interoperability requirements. Upload batching, compression decisions within a supported encoding and pack composition can change while old valid manifests remain readable. Changing an identifier derivation creates a different object namespace. [Data model](data-model.md) · [Remote layout and publication](remote-layout.md) · [Journal format](transaction-journal.md)

## Protocol transitions

Each daemon requires sole ownership of every address it binds. With Web configured for `127.0.0.1` and port zero, one daemon can serve IPC and browser clients on its own ephemeral socket. If another listener owns the configured address, startup fails before the daemon publishes discovery metadata. A successful HTTP response from an occupied port is insufficient to identify the intended daemon. [HTTP API](../http-api.md)

1. **Bootstrap.** The initializer registers a writer before executing a parentless publication. At admission it must see its own writer as the only writer, then read fresh HEAD and Epoch listings. A fresh bootstrap requires both to be empty. A journal resuming a root publication may encounter its own recorded evidence. An unexpected marker or Epoch stops publication. On a backend with the visibility properties above, a later overlapping initializer sees the first writer while it is active, or sees its publication after that writer releases its registration. Failure can make both initializers retry. This costs additional control reads only on the bootstrap path.
2. **Observe and plan.** A returning client loads its local base and authenticates the observed history against its applicable checkpoint. A missing Epoch inventory with a supplied checkpoint is a conflict. Failures and cancelled requests preserve uncertainty. Missing required payloads can leave pending materializations. They do not authorize deletion. A destructive empty-root plan is subject to the Sync safeguard on reobservation as well as initial planning. [Synchronization](synchronization.md)
3. **Publish.** Verify required content and the commit representation, publish and verify the exact HEAD, then accept the state in SQLite after the required Epoch checks. A successful PUT alone does not establish durable local acceptance. A remote commit can be visible before its publishing client updates SQLite. Independent writers can publish children of the same parent. Later reconciliation uses the observed logical heads and preserves conflicting content according to the path rules. An offline device returning with its local base commit strictly behind an advanced Epoch (`epoch_advanced` and `local_generation < anchor.height`) retains its expired base tree read-only to fast-forward untouched remote updates while preserving local edits and never emitting deletions from the expired base alone. Eventual reconciliation requires successful retries, sufficiently complete observations and a period without conflicting changes. [History and concurrency](history-and-concurrency.md) · [Reconciliation](reconciliation.md)
4. **Recover.** Use the authenticated local journal and the observed publication evidence to choose rollback, roll-forward or a stop for uncertainty. A peer can legitimately prune an ancestral HEAD between remote publication and local cleanup. At `DatabaseCommitted`, recovery can finish with proof of ancestry from the current authenticated history and agreement with the durable local state and pending intent. A contradictory marker, divergent local state or unavailable proof retains recovery evidence. For GC, a `.pending-gc-epoch` local record preserves an in-flight successor Epoch publication across lost responses or restarts so recovery reconciles the exact remote state instead of publishing a conflicting `N+1` object. [Phase-by-phase recovery](transactions-and-recovery.md)
5. **Retain.** Ordinary 0.32 Sync creates Epoch zero at bootstrap and keeps `EpochAdvancementPolicy::DeferMultiWriter` on established vaults: writers never race to publish `N+1` Epochs during normal synchronization, while still validating and adopting any valid successor confirmed on storage. Frontier advancement is concentrated in explicit maintenance [`kasumi gc`](garbage-collection.md) under the cooperative maintenance barrier. When history strictly behind a reachable boundary satisfies both minimum shortest depth from logical heads/marked commits and minimum superseded age (default `5` generations and `6` hours from child superseding timestamps, clamped against `min(local_now, barrier_remote_now)`, independent of file `mtime` and separate from physical deletion grace `--min-age`), GC revalidates barriers, `epochs/`, and `heads/`, persists `.pending-gc-epoch`, publishes and verifies `N+1`, updates the local Epoch checkpoint, and runs a second full observation under `N+1` before any physical deletion. Merge bases between multiple unreconciled logical heads remain protected. Lowering retention settings or removing an ancestral HEAD marker never discards history during ordinary Sync; running GC is what advances the authenticated frontier when history qualifies. [Retention horizon](history-and-concurrency.md)
6. **Maintain.** Fsck verifies observations. GC plans Epoch advancement and physical deletions from authenticated reachability and storage inventory under a cooperative barrier, with grace, pre-publish and mid-Apply revalidation checks (`--dry-run` simulates Epoch advancement in memory without writing remote Epochs or removing objects). Repack publishes a representation change and has its own maintenance and reclamation preconditions. An indeterminate write or removal must be reconciled before claiming success. An abandoned writer or barrier may block work after a crash. A timestamp alone cannot distinguish an abandoned operation from a slow one. [Fsck](fsck.md) · [GC](garbage-collection.md) · [Repack](repack.md)

## Failure cases and accepted costs

Verification at publication can use a provider-reported physical hash, with verified readback as a fallback. Accepting an observed commit requires client-side cryptographic authentication. A provider's hash response cannot establish independent evidence of durable storage. [Remote verification](remote-layout.md)

Three invariants connect the transitions.

- **Publication.** Every newly published HEAD references a commit representation checked by the publisher. Its snapshot or manifest names the required content. Publication order lets a reader discover the commit through HEAD. Continued availability depends on storage retaining the referenced objects.
- **Continuity.** An exact local Epoch checkpoint must belong to the chain used for acceptance. Matching a sequence number alone is insufficient. The local base commit can fall outside retained ancestry only under the authenticated horizon rules. [History and concurrency](history-and-concurrency.md)
- **Collection.** Start at every valid physical HEAD, walk parent edges to the authenticated anchors, and mark the required commit variants and manifest-referenced objects. Protect at least one usable variant of every retained commit and every exact variant selected by a HEAD. A deletion plan additionally needs the local checkpoint checks, a complete inventory, the grace checks and an exclusive maintenance registration. [GC](garbage-collection.md)

Enrollment starts after the initializer has accepted its first commit and Epoch locally. HEAD publication precedes Epoch publication. A device attaching in that interval can observe valid commit history with no Epoch, a view also supported for older vaults. If bootstrap is interrupted, recover the initializing profile before admitting peers. The sole-writer bootstrap check prevents competing roots on a conforming store. It does not make the HEAD and Epoch writes a single remote transaction.

Ordinary writers can accumulate history up to the implementation bounds unless periodic maintenance GC advances the retention Epoch. The current graph reader permits 4,096 loaded commits, 4,096 levels of graph depth and 64 marked heads; an individual commit permits 32 parents, and an Epoch permits 64 boundary anchors. Vaults running GC regularly before crossing 4,096 retained commits keep the reachable DAG compact across `0 -> 1 -> 2 ...` Epochs, whereas a vault whose retained history already exceeds 4,096 commits stops traversal with a limit error. [Graph limits](../../include/core/history.hpp)

| Observable situation | Required outcome | Cost or boundary |
|---|---|---|
| Two devices observe an empty destination | Refuse competing genesis admission. Reobserve after the other writer finishes. | Temporary unavailability, including after an abandoned registration. Deploy corrected writers throughout the vault. |
| Two writers publish different children on an established vault | Both children can be heads. Reconcile the observed branches without overwriting a single shared head pointer. | Branches and conflict files consume space. Clients can temporarily see different snapshots. |
| A returning device supplies an Epoch checkpoint and the store lists no Epochs | Return conflict. Preserve the accepted checkpoint. | An empty listing cannot safely distinguish loss, deliberate suppression and a misconfigured destination. |
| A device with no prior checkpoint receives an older valid chain | It can authenticate the presented chain. Its freshness remains unknown. | Detecting a consistently withheld successor would require an independent witness. |
| Storage accepts a registration but its response or verification fails | Retain evidence of the uncertain registration. Reconcile the exact owned object. Preserve a replacement belonging to another writer. | Extra local state and sometimes operator intervention. |
| A rooted, valid Epoch chain forks at the same sequence | Stop chain selection and destructive GC. Preserve both branches and checkpoints for inspection. | No automatic tie-break can honor two incompatible exact checkpoints. |
| The GC inventory omits the collector's accepted commit or exact Epoch | Stop both dry-run and live GC before classifying or removing candidates. A retained ancestor commit and a predecessor Epoch remain acceptable. | The collector reads its persisted state. A device whose base falls behind the retained graph must synchronize before collection. |
| A malicious provider hides reachable history during GC | The collector can only protect reachability visible under its inventory assumptions. | Cryptographic authentication and age checks cannot prove completeness. Destructive collection requires a trustworthy inventory and coordinated writers. |

## Compatibility and change control

Use a single initializer on upgrade and complete pending transactions with a compatible reader. Two earlier clients can still race to advance an Epoch. A new client sharing their destination cannot prevent their writes. For an already bifurcated vault, preserve its objects and local checkpoints, suspend destructive maintenance, and inspect each candidate by exact ID. No branch is authorized for deletion solely by its timestamp, ID order or majority of observed devices.

An incompatible change to canonical bytes, key purposes, published names, acceptance rules, or the meaning of a deletion proof requires an explicit format or protocol revision. Specify old-reader and old-writer behavior, interrupted-upgrade recovery and a fixture for the prior format before enabling the new writer. Reopen these decisions for a demonstrated safety violation, a cryptographic break, an incompatible requirement or an operational limit that invalidates the deployment assumptions.

## Evidence and evaluation

For an Epoch v1 interoperability vector, use the 32-byte master key `00 01 … 1f`, vault ID `aa` repeated 32 bytes, sequence 2, issuance time 1800000000, retention depth 5 and age 6 hours. The predecessor is `bb` repeated 32 bytes. The ordered anchors are `cc` repeated 32 bytes at height 40 and `dd` repeated 32 bytes at height 41. The 177-byte canonical payload yields the Epoch ID `b07e214ab8b1bece7e6af3c26f9dc1f0c71e43668cb1e88cde40ad25b4b55e01`. [Epoch codec fixture](../../tests/unit/application/history_storage/test_epoch.cpp)

The executable selection is labeled `release-critical`. It covers visibility and checkpoint failures, multi-writer retention, ancestral-marker recovery, reachability and failed cleanup. These are implementation regressions on controlled backends. They establish neither formal verification nor the consistency of every rclone provider. [Test selection](../../tests/release_critical_labels.cmake) · [Build and test](../build-and-test.md)

For a paper, evaluate initial upload and enrollment separately from steady-state sync. Report client and provider versions, dataset shape, number of devices, backend consistency assumptions, bytes transferred, object requests, retained bytes and recovery time after interruption. Report competing-genesis refusal separately from successful concurrent branch publication. Performance and scalability claims require measurements for those workloads.

The organization into system model, security assumptions and evaluation follows the supplied UPSS paper as a reference for exposition. Kasumi's shared vault key, commit DAG and maintenance contract are described and tested independently.
