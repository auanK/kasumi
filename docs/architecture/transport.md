# Transport and Provider Capabilities

Kasumi's logical protocol operates on immutable content, Commit variants, physical markers, Epochs, and maintenance controls described in [Remote Layout and Publication](remote-layout.md). `Transport` only moves and lists physical objects. A backend does not resolve the DAG, decide logical heads, decrypt payloads, or certify a publication as valid on its own.

The required storage operation table is `initialize`, `put`, `get`, `presence`, full `list`, and idempotent `remove`. Identifiers are validated as relative, normalized paths without traversal. `open_transport` selects a local filesystem backend for absolute paths (including Windows drives/UNC paths) or an already configured `rclone` remote for `name:relative/root`, and accepts `TransportOptions` to pass optional `rclone_config` (`RCLONE_CONFIG`), `bandwidth_limit` (`RCLONE_BWLIMIT`, validated via `validate_bandwidth_limit`), and `forbidden_executable_root`. The local backend maps object identifiers under its configured directory. For rclone, Kasumi resolves an allowed executable outside the synchronized root, starts a child `rclone rcd` session on authenticated loopback RC (`--rc-max-header-bytes 65536`), verifies its PID, readiness, and minimum `rclone` version (`v1.60.0` via `core/version`), maintains a thread-safe keep-alive HTTP client pool (`RcRuntime`, up to 16 pooled connections) to reuse loopback TCP sockets across concurrent RC requests while monitoring both global cancellation and per-request `std::stop_token`, and stops the daemon when the transport closes. Read-only environment checks (`probe_rclone_installation`, surfaced by `kasumi diagnostics`) reuse the same executable-resolution and minimum-version validation without starting a daemon or accessing remotes. The child receives controlled RC credentials and excludes `KASUMI_` environment variables. Backends return normalized error categories such as not found, permission, I/O, process/protocol failure, timeout, cancellation, or backend unavailable. Ambiguous mutations require follow-up observation; `remove` checks presence after an ambiguous failure.

At shutdown, Kasumi drains in-flight RC requests, asks the daemon to quit, and closes the HTTP pool. An acknowledged `core/quit` lets Kasumi terminate its child immediately. The regular wait, terminate, and kill sequence remains the fallback.

Optional transport capabilities include metadata listing (`list_metadata`, returning sorted `ObjectMetadata` with Unix timestamps and byte sizes via `operations/list` with `noModTime: false` on rclone or native stat on local), prefix listing, same-storage copy, explicit copy/PUT/removal batches, directory-based PUT/GET batches, ordered control-read batches, and individual or batch physical SHA-256. Missing capabilities report `Unsupported` where the wrapper has no direct fallback. Metadata listing falls back to `list` for callers when `Unsupported`, while garbage collection treats missing timestamps fail-safe under positive `--min-age`. Directory-based PUT/GET batches fall back to individual calls; higher layers handle explicit batch `Unsupported` with individual operations or a verified workspace path. Control reads fall back to ordered listing and presence calls. A batch `Unsupported` result must mean no item was submitted; other partial or ambiguous failures are treated as failures, not silently replayed. The rclone backend may use native remote operations and bounded batch concurrency; the local backend provides filesystem operations. Capability availability is backend/provider dependent and is not part of Kasumi's logical format.

The required operation table does not imply a consistency model. Online destructive maintenance relies on completed control-object and namespace mutations becoming visible to the `LIST` and `PRESENCE` observations used by its protocol. The maintenance probe checks only whether its own new temporary object appears and disappears in listings; a successful probe cannot certify visibility of every existing object or rule out a stale listing that omits an older writer marker. Provider consistency must be confirmed independently. Providers without suitable guarantees are not established as safe for online destructive GC merely because the probe passes.

**Physical hash** means SHA-256 of stored ciphertext or marker bytes, distinct from a plaintext BLAKE3 **logical hash**, a keyed Content/Commit ID, and a BLAKE3 Ciphertext ID. When a provider returns remote SHA-256, publication and maintenance compare it with a locally computed expected hash. This is a provider-supplied transport check, not proof against a malicious provider; protected payloads are authenticated when loaded. If the capability is `Unsupported`, the verified fallback downloads bytes and compares physical bytes or authenticates/decrypts according to the object type. A malformed hash, mismatch, missing object, or other transport failure is not treated as successful verification.

Rclone batch SHA-256 verification uses an exact file list with `FilesFromRaw` and
`NoTraverse`, alongside its checksum manifest. It queries only the requested
objects instead of recursively listing unrelated Content and history. Both
temporary files are removed after the request, including failed responses.

Rclone uploads use `NoCheckDest` to avoid the copy layer's redundant destination
lookup. Provider PUT semantics still apply, and Kasumi's physical verification
after upload is unchanged. Each FastCDC download window supplies the content
concurrency as rclone's transfer limit. The copy deadline applies per window.

The local backend stages PUTs under `.kasumi-staging`, outside writer and barrier namespaces. Concurrent PUTs sharing the backend state hold staging leases so one worker cannot remove the staging directory while another uses it. The scope of that coordination is the local backend instance. Across devices, bootstrap and maintenance depend on acknowledged writes becoming visible to GET and prefix LIST and on complete listings. [Vault protocol](protocol-0.32.md)

## Control Read Batches

`control_read_batch` aggregates read-only remote checks during observation and writer admission into single backend requests (such as rclone `job/batch`). Batches containing directory prefix listings (`list_prefixes`) preserve strict sequential execution (`concurrency = 1`) to uphold control ordering (`LIST writers/barriers -> STAT legacy barrier`). Independent content presence checks (`presence_identifiers` only) are partitioned into bounded chunks of up to 128 items executed with bounded concurrency (8 workers) to prevent request deadlines from expiring on large vaults. Results are correlated positionally, and any transport, parse, or timeout error fails closed without converting failures into false content absences.

## Transfer telemetry

Payload copies with a progress observer use rclone's asynchronous RC jobs. Each job has a unique stats group. Kasumi polls job status and core stats about every 250 ms and sends a best-effort job stop on cancellation. The original paths and batch inputs still govern the copy. Synchronous copy responses and transfers without a progress observer retain the existing result checks.

Local copies with an observer stream in 256 KiB blocks into the same atomic staging flow. Transport counters track bytes and objects reported by these copies. The transfer mechanism introduces no content presence probes.
