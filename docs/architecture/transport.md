# Transport and Provider Capabilities

Kasumi's logical protocol operates on immutable content, Commit variants, physical markers, Epochs, and maintenance controls described in [Remote Layout and Publication](remote-layout.md). `Transport` only moves and lists physical objects. A backend does not resolve the DAG, decide logical heads, decrypt payloads, or certify a publication as valid on its own.

The required storage operation table is `initialize`, `put`, `get`, `presence`, full `list`, and idempotent `remove`. Identifiers are validated as relative, normalized paths without traversal. `open_transport` selects a local filesystem backend for absolute paths (including Windows drives/UNC paths) or an already configured `rclone` remote for `name:relative/root`. The local backend maps object identifiers under its configured directory. For rclone, Kasumi resolves an allowed executable outside the synchronized root, starts a child `rclone rcd` session on authenticated loopback RC, checks its PID/readiness, and stops it when the transport closes. The child receives controlled RC credentials and excludes `KASUMI_` environment variables. Backends return normalized error categories such as not found, permission, I/O, process/protocol failure, timeout, cancellation, or backend unavailable. Ambiguous mutations require follow-up observation; `remove` checks presence after an ambiguous failure.

Optional transport capabilities include prefix listing, same-storage copy, explicit copy/PUT/removal batches, directory-based PUT/GET batches, ordered control-read batches, and individual or batch physical SHA-256. Missing capabilities report `Unsupported` where the wrapper has no direct fallback. Directory-based PUT/GET batches fall back to individual calls; higher layers handle explicit batch `Unsupported` with individual operations or a verified workspace path. Control reads fall back to ordered listing and presence calls. A batch `Unsupported` result must mean no item was submitted; other partial or ambiguous failures are treated as failures, not silently replayed. The rclone backend may use native remote operations and bounded batch concurrency; the local backend provides filesystem operations. Capability availability is backend/provider dependent and is not part of Kasumi's logical format.

**Physical hash** means SHA-256 of stored ciphertext or marker bytes, distinct from a plaintext BLAKE3 **logical hash**, a keyed Content/Commit ID, and a BLAKE3 Ciphertext ID. When a provider returns remote SHA-256, publication and maintenance compare it with a locally computed expected hash. This is a provider-supplied transport check, not proof against a malicious provider; protected payloads are authenticated when loaded. If the capability is `Unsupported`, the verified fallback downloads bytes and compares physical bytes or authenticates/decrypts according to the object type. A malformed hash, mismatch, missing object, or other transport failure is not treated as successful verification. Native copy is used only with an expected source hash and destination verification; otherwise GC can copy through a local workspace with readback. Provider certification details stay in [Provider Certification](../provider-certification.md).
