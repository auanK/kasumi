# Profile Management

`kasumi config` is the interactive CLI (with optional `rclone listremotes` destination hints), `kasumi profile <create|edit|clone|storage|rename|delete|test>` is the non-interactive CLI for managing and verifying profiles and key storage modes, `kasumi ignore <check|init>` evaluates and scaffolds `.kasumiignore` rules, and `kasumi key <profile> [--replace]` prompts or uses environment credentials to re-enter or replace a profile's stored key (without re-encrypting the vault). These commands change local configuration, `.kasumiignore`, OS vault entries, and private profile storage, **not** synchronized payload state or remote vault objects. The command options and wizard prompts are in [Configuration and Usage](../configuration-and-usage.md); [Application and Runtime](application-and-runtime.md) owns runtime resolution and private-state layout.

## Ownership and credentials

Deleting a profile in the wizard requires explicit confirmation, defaulting to
No. Before confirmation it shows the selected profile and its paths, and explains
that configuration, key (in `key.bin` and/or the OS credential vault), and local state are removed while synchronized files
and remote data remain intact. EOF or cancellation preserves the profile.

Editing paths shows the old and new local and remote destinations before asking
to save, defaulting to No. Changing settings does not move local files or migrate
remote data; selecting an empty local folder can plan deletions during a later
Sync. Review `kasumi status <profile>` before syncing after a path change.
Declining, EOF, or cancellation leaves configuration and profile state intact.
Keeping both paths unchanged does not rewrite the configuration.

Clone, rename, edit, key entry, key-storage change, and delete validate the selected existing profile before
asking for later fields. An unknown name repeats the selection prompt without
discarding other accepted input or changing profile data.

`kasumi list` prints only configured profile names, one per line. `kasumi show <profile> [--full]`
shows the selected profile's local path, remote destination, `key_storage` mode (`vault`, `file`, or `memory`), retention settings, local state, and offline local traceability (`accepted_commit_meta`, last complete sync, last local attempt, local maintenance summary, and any offline-cached remote maintenance records with `--full` expanding complete IDs and histories). Neither query contacts remote storage or changes persistent profile data (SQLite snapshots are always copied to temporary storage before inspection); credentials are never displayed. The wizard lists names, states, and a compact last-sync summary column; paths and retention details are available through `show`.

When `show` reports `Problem`, it also explains the first issue detected during
that same local inspection, such as an unavailable key, invalid database, invalid or unreadable
profile lock, unsafe sidecar, or inspection-workspace failure. While an active Kasumi operation legitimately holds the lock, `config`, `show`, and `diagnostics` report `Running` (e.g. `Running (gc)`) instead of `Problem`. This inspection does not repair state or imply that no other issues exist.

`config.toml` at the application data root owns named profiles: absolute synchronized `local_dir`, local or rclone `remote_dir`, positive history-retention depth/age, and required `key_storage` (`vault`, `file`, or `memory`; new profiles default to `vault`). Each profile has a separate `profiles/<name>/` private directory, SQLite state, local operation lock, and—depending on `key_storage`—an OS vault credential (`kasumi/<name>`), a local `key.bin`, or no persisted key (`memory`). A profile name must be safe for a child of `profiles/`. Configuration is saved by atomic private-file replacement; loading it may enforce owner-focused permissions. Configuration mutations are serialized by `config.lock` at the application data root, with a bounded acquisition wait. This lock is distinct from per-profile execution locks; configuration reads do not acquire it. Separate profiles do not implicitly share an accepted base or key; to use one vault on another machine, configure the same remote destination and master key. Creating a profile does not publish remote history.

The creation and key-entry APIs accept either a 32-byte master key encoded as hex or a Password/Password Salt pair; the interactive wizard and `kasumi key <profile>` prompt for the pair and derive the key with Argon2id. Depending on `key_storage`:
* `vault` stores the 32-byte key in the OS credential vault (Windows Credential Manager on Windows; Freedesktop Secret Service / GNOME Keyring or KDE KWallet loaded on demand via `dlopen` on Linux).
* `file` writes `profiles/<name>/key.bin` using reversible XOR masking plus filesystem access controls, **not** encryption at rest.
* `memory` skips key persistence; each runtime operation derives or receives the key in memory.

Routine operations read the persisted key from the configured backend (`vault` or `file`), or prompt/read environment credentials in `memory` mode; when a persisted key exists, a supplied `KASUMI_MASTER_KEY` must match it. Switching `key_storage` removes the key from the previous storage backend and requires `kasumi key <profile>` (or `[k] Key`) when switching to `vault` or `file`. See [Security](../security.md).

## Operation flows

| Action | Validation, state transition, and failure boundary |
|---|---|
| List | Load and parse `config.toml` (`version = 1` or unversioned), return its profiles; a missing file means an empty list, while malformed configuration or an unsupported version is an error. No key, transport, local tree, or remote object is opened. |
| Create | Validate the proposed settings and credentials. With `--verify`, test the candidate destination and key before exposing the name. Under the configuration lock, recheck name and private-path availability, initialize private state and persist the configuration. Verification failure or cancellation does not publish the candidate. |
| Test | Load profile configuration and credentials (`vault`/`file`/runtime `MasterKeyBytes` or `PasswordPair`), list remote storage via `transport`, and if non-empty run read-only `observation::history::observe(..., false)` to distinguish `EmptyReadyForInit`, `AuthenticatedVault`, `KeyMismatchOrInvalidHistory`, and `TransportFailure` without modifying local or remote state. |
| Ignore check / init | `check_profile_ignore` evaluates paths against `.kasumiignore` and reserved internal rules via `ignore::inspect_ignore`, reporting disposition plus matched line/rule text. `init_profile_ignore` creates (`default`, `dev`, `office`, `minimal`) or previews (`dry_run`) `.kasumiignore` in `local_dir` (atomic create-only installation by default, including when another process creates the file after preview; `force` permits replacement). |
| Clone | Copy the source configuration (including optional transport settings) and persisted master key (if present in `vault` or `file`) into a new private directory/vault entry, initialize a new empty SQLite database, and persist the new profile. It does not copy accepted state, history, or Sync journals. Rollback records the identities of created files and removes only matching entries; unknown or replaced files remain and make rollback report an error. Windows removes files and the final directory through checked handles. POSIX unlink and directory removal are name-based, so same-UID races during identity capture or final removal are outside the guarantee; private-directory permissions exclude other user accounts. |
| Edit | Validate the new absolute local path, remote location, and optional transport settings (`bandwidth_limit`, `transfer_concurrency`, `rclone_config`); block moving `local_dir` of a populated profile onto a missing or empty directory unless `allow_empty_local` is set; the non-interactive CLI passes the expected profile revision so a concurrent edit can be rejected before saving. Name, `key_storage`, and key stay as they were. It does not move either the existing synchronized directory or private state, rekey the vault, or migrate remote history. Missing/malformed configuration, absent profile, or failed save stops the edit. |
| Key / Storage | `[s] Storage` changes `key_storage` (`vault`, `file`, `memory`), saves `config.toml`, and deletes any key persisted in the old backend. `[k] Key` and `kasumi key <profile> [--replace] [--json] [--quiet]` derive the 32-byte key from Password and Password Salt (or read `KASUMI_MASTER_KEY` / `KASUMI_PASSWORD` + `KASUMI_PASSWORD2`) and store it in the active backend (`vault` or `file`); they succeed without rewriting when the stored key already matches, require confirmation or `--replace` before overwriting a different valid key (`AlreadyExists` / `already_exists` in non-interactive `--json` mode), and do not re-encrypt remote vault data. |
| Rename | Validate the new name, reject a duplicate name or occupied target private path, resolve both private paths, move the existing private directory (and migrate any `vault` credential from `kasumi/<old>` to `kasumi/<new>`) if present, then save the renamed configuration. If saving fails, it attempts to move the private directory and vault entry back and reports a rollback failure if that also fails. The key and SQLite state move with the profile; synchronized and remote paths do not move. |
| Delete | With configuration and profile locks held, persist deletion intent and remove the configuration entry. Retire the private directory, clean up the credential and retired state, then release the name reservation. An interruption can leave the profile absent from the list but its name reserved. Retry deletion by name to finish. Synchronized files and remote objects survive profile deletion. |

## Local profile states

The wizard passively inspects each profile and displays one of five local states. `Initialized` means the profile infrastructure is valid (or `key_storage = "memory"`, where key presence is not required on disk) but the database has no accepted state. `Ready` means an accepted state is valid and has no pending materializations. `Pending` means a valid copied database has pending materializations or an active authenticated Sync or SQLite rollback journal. `Running` means another Kasumi execution currently holds a valid exclusive OS file lock on the profile (annotated with the active operation when an `InProgress` local execution record is visible, such as `Running (sync)` or `Running (gc)`; `--json` exposes `"state": "running"`, `"lock_active": true`, and `"active_operation"`). SQLite recovery, when needed, runs only on the temporary copy. `Problem` means required infrastructure (including a missing `vault` or `file` key, or a malformed/unreadable lock file) is invalid, corrupted, inaccessible, or could not be inspected safely. Inspection does not run Sync, contact the remote, or change persistent profile data.

The database classification describes the temporary SQLite view acquired during that inspection; it is not a promise that the result includes every commit made before inspection returns. A writer can commit during inspection and still be absent from the result when the copied files represent an earlier consistent SQLite view; a later inspection sees that commit. The snapshot is rejected as `Problem` when an included source file's identity, native timestamps, or content changes during acquisition.

Profile-management actions do not enter the Sync transaction recovery, [Fsck](fsck.md), or [Garbage Collection](garbage-collection.md) flows. Editing a destination or deleting a key can make later access to a vault impossible unless the original key and destination are retained elsewhere; it is not a remote migration or remote delete operation.
